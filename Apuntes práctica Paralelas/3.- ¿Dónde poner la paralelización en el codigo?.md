Para poder tener en claro dónde tener cada punto de paralelización, tendriamos que tener en cuenta no poner de manera excesiva ni abusar del mismo para no crear más hilos de los que realmente son necesarios. Afortunadamente, en el código la mayoria de paralelización no afecta a un resultado en concreto, por lo que no tenemos que hacer apenas uso del `reduction` sin muchas consecuencias.

OJO: no hace falta paralelizar todos los bucles y todas las partes que señalo, eso depende del número de funciones, variables y monomios con la que el programa trabaja para saber cuán de beneficioso es o no.

## 1.  calcular_gradientes()  -> funciones
Cada iteración de este método trabaja con una función distinta:

```text
i = 0 -> funciones[0]
i = 1 -> funciones[1]
i = 2 -> funciones[2]
...
```

Y cada una escribe el resultado en una zona diferente:

```text
funciones[0] -> gradientes[0]
funciones[1] -> gradientes[1]
funciones[2] -> gradientes[2]
...
```

Lo que implica que todas las funciones se pueden calcular de manera independiente, lo que conecta con una posible paralelización utilizando: `#pragma omp parallel for`, sin reduction ni similar, pues cada hilo creado escribe en `gradientes[i]`, es decir, en una posición diferente.

El rendimiento de este método sería menor si el código realiza pocas funciones a la vez, como 2 o similar, lo que apenas aprovecha la paralelización. Así que, para medir el rendimiento real necesitaremos más funciones a calcular.

## 2. calcular_gradiente() -> variables y monomios
En el primer bucle de este método:

```C
    for(int variable = 0; variable < funcion->num_variables; variable++) {
        double derivada = 0.0;
		....
	}
```

Cada iteración calcula una derivada parcial diferente.

```text
variable 0 -> df/dx
variable 1 -> df/dy
variable 2 -> df/dz
...
```

Por ende, al ser independientes entre sí,  lo que hace fácilmente paralelizable con: `#pragma omp parallel for` donde cada hilo se encargara de una o varias variables.

Como en el caso anterior, esta alternativa es interesante si una función tiene muchas variables, sino, no se aprovecha del todo la paralelización.

___

Ahora, para el bucle de monomios:

```C
for(int m = 0; m < funcion->num_monomios; m++) {
    derivada += derivar_monomio(&funcion->monomios[m], punto, 
	    funcion->num_variables, variable);
}

```

Al calcular una derivada parcial, hay que sumar la contribución de todos los monomios, es decir:

```text
para df/dx (donde cada punto x, y, z son -> 1, 2, 3):

3xy -> 6
4yz -> 0
2x -> 2
5 -> 0

total = 8
```

Aunque cada monomio se puede derivar independientemente, el resultado total se debe sumarse a la misma variable `derivada`, lo que provocaria una condición de carrera que para solucionar, habría que paralelizarlo mediante reducción: `#pragma omp parallel for reduction(+:derivada)`.

Se aprovecha sobre todo cuando la función tiene una cantidad grande de monomios.

## 3. RESULTADO FINAL

En resumen, la paralelización y su rendimiento depende de cuántas funciones, variables y monomios tengamos que calcular, la paralelización en uno o varios bucles puede ser tanto una ventaja como una desventaja, porque depende de sobremanera cuántas hay que hacer. 

### Resumen
Vamos a ir comprobando en cada prueba el rendimiento de cada caso cuánto afecta el número de funciones, variables y monomios, y ver hasta qué punto es rentable tener una, dos, o todo paralelizado o prácticamente nada paralelizable.
